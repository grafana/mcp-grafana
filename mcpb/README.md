# MCP Bundle

Sources for the [MCP Bundle](https://github.com/modelcontextprotocol/mcpb) (`.mcpb`) that Claude
Desktop installs. Each release attaches a built `mcp-grafana_<version>.mcpb`.

| File | Purpose |
|---|---|
| `manifest.template.json` | Bundle metadata. `version` and `tools` are filled in at build time; everything else ships as-is. |
| `launch.sh` | Picks the Linux binary matching the machine's CPU architecture. |
| `icon.png` | Bundle icon, 512×512 as Claude Desktop prefers, rendered from `icon.svg`. |

`scripts/build-mcpb.mjs` assembles the bundle. It stages the binaries GoReleaser built, generates
the manifest, and packs the result. The `tools` array is generated by starting the freshly built
server and calling `tools/list`, so the bundle cannot advertise tools the server does not have.

## Building locally

```bash
goreleaser build --snapshot --clean --id mcpb
node scripts/build-mcpb.mjs
```

The bundle lands in `dist/`. To inspect it, unzip it — a `.mcpb` is a zip archive.

## Why Linux needs a launcher and macOS does not

An MCPB manifest can vary the server command per operating system, but not per CPU architecture:
the resolver matches on the OS alone, and no manifest version has an architecture field
([modelcontextprotocol/mcpb#10](https://github.com/modelcontextprotocol/mcpb/issues/10)). An
architecture-keyed override validates and is then ignored.

macOS therefore gets a single universal binary carrying both architectures. Linux has no equivalent
format, so it ships both binaries behind `launch.sh`. Windows ships one amd64 binary, which Windows
on ARM runs under emulation.

## Signing

Bundles are unsigned: `mcpb sign` needs a code-signing certificate we do not have.
